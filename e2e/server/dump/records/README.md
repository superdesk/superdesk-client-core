# Can easily be ported to main snapshot:

* editor3-tables - adds tables formatting option to story content profile.
* ordered-list - adds the `ordered list` formatting option to story/body_html content profile. A single `content_types` update event on top of `main`, so it does not carry the auth/activity churn a UI recording picks up.
* editor3-comments - adds the `comments` formatting option to the Story profile's body_html field, which is what puts the Comment button on the editor3 toolbar and makes inline comments reachable at all. No content profile in `main` or in any other record based on it enables it; the only other snapshot that does is `legacy`, whose own user database rules out any two-user flow. A single `content_types` update event on top of `main`, so it does not carry the auth/activity churn a UI recording picks up.
* custom-blocks - adds custom blocks to story/body_html content profile. Creates a new custom block vocabulary.
* compare-fields - adds urls/boolean/manual-entry-dropdown custom fields and a populated dateline to the Story profile, with two article versions carrying differing values. Used to exercise the compare-versions and print-preview field rendering.
* editor3-formats - the full editor3 toolbar on the Story profile. `body_html` gains every heading level, `strikethrough`, `subscript`, `superscript`, `pre`, `unordered list`, `ordered list` and `formatting marks` on top of the nine options `main` ships, and a custom editor3 text field "Sample rich text" (vocabulary `sample_rich_text`, `field_type: "text"`) is added to the content section with the same list. `main` carries no custom text field at all, so this is the only snapshot in which a formatting case can be repeated against one. Kept out of `main` for now because open specs assert `main`'s toolbar contents.
* editor3-suggestions - the same toolbar as `editor3-formats` with `suggestions` added, on both `body_html` and the custom editor3 text field "Sample rich text", plus the Sports desk article "story with suggestions". No other snapshot enables `suggestions` on any field, and the suggestions-mode cases need it on the body and on a custom text field, which is what their prerequisites ask for. It duplicates `editor3-formats` rather than extending it because a record is a patch on a full dump and cannot be layered on another record. Fold the two together the day `editor3-formats` can be re-recorded, and until then keep the format lists in step. The article's body reads `alphabravocharliedeltaechofoxtrot`, six words run together with no separators between them, where `bravo` and `foxtrot` are insertion suggestions and `delta` is a deletion suggestion, all by `admin` and all unresolved: it is the "article with existing suggestions" the accept and reject cases start from, and `foxtrot` is the one they leave alone so a resolved article still carries one. A suggestion is draft.js editor state under `fields_meta`, not markup, so it is recorded like any other field the browser writes. Only the archive item, its versions and its history were kept from that recording session; the lock/unlock, audit, activity and session writes around it were dropped.
* authoring-extras - "test sports story" carrying `keywords` and an `expiry` of 2099-12-31, which the Info widget needs to render its Expiry line and its keywords line on an editable item. In `main` only spiked items have an expiry. The keywords row is a second row reusing the "Word Count" label (an upstream mislabel, its `ng-if` is on `item.keywords`) and `main` already renders the real Word Count row, so locate the keywords row by position or by content, never by label. The recorded API write also re-versioned the item: `versioncreated` moved to 2026-08-08 and `_current_version` went from 2 to 3, so under this snapshot the item sorts to the top of Sports / Working Stage (monitoring sorts `versioncreated:desc`) and shows one more version than under `main`. `expiry` is derived from desk settings server-side and is not writable through the archive API, so it was set in mongo directly. The date is far future on purpose: snapshot dates are absolute and are never relativised at restore, and an expired item is a candidate for the content-expiry job.
* saved-search-private - "Shire drafts", a saved search with `is_global: false` owned by `admin`, so the private saved-search list is not empty for the default session. `main` has two global searches and no private one. It stays a record only until the monitoring-settings spec covering the saved searches tab stops seeding its own private search through the UI: that spec asserts the private list holds exactly one.
* authoring-header - state the authoring header row needs and `main` lacks: `signal` plus `correction_sequence` on "test sports story", the legal/sms/not-for-publication flags plus `rewritten_by` on "story 2", a two item translation chain ("Header translations original" / "Header translations german"), "Broadcast of Story 5" (a broadcast item whose `broadcast.master_id` points at the published "Story 5", for the MASTER block), and two more items sharing the slugline "Story 3". "Story 3 sibling" makes "Story 3" show the Missing Link label; "Story 3 rewrite" has the same sibling but carries `rewrite_of`, so it covers the case where the rewrite link alone suppresses the label. The sibling is dated 2099 on purpose: Missing Link only counts related items created since midnight, snapshot dates are absolute and are never relativised at restore, so a future date is the only one that keeps matching as time passes.

# Must stay out of the main snapshot:

* publishing - the unfiltered product "All content" and the subscriber "Public API", whose only destination formats as `ninjs`. `main` ships one subscriber, "Subscriber 1", whose destination formats as `email`, so under `main` alone there is no NINJS output to assert on. It cannot be ported: `subscribers.spec.ts` asserts `main` lists exactly one subscriber, and that count is the point of the test, not an incidental detail. Modelled on `legacy`'s "Public API", with one deliberate difference. Legacy delivers by `http_push` to `http://localhost:5050/publish`, which nothing in the e2e stack answers, so that transmission never completes and its queue entries never reach `success`. This one delivers by `email` to the mailcrab the stack already runs; the email transmitter falls back to sending `formatted_item` verbatim when it is not email-formatted, so the payload stays NINJS and the entry reaches `state: "success"`. The product carries no content filter, unlike `main`'s "Product 1", which blocks the Sports slugline conditions. Publishing without picking a target subscriber queues two entries per item here, one per subscriber, so address a queue row by its Subscriber or Destination column and never by headline alone, or the locator matches two rows and Playwright raises a strict-mode violation.

* association-fields - `main` plus the two association fields the locked-item publishing and correcting cases need on the Story content profile, and the items to put in them. "Shire related items" (vocabulary `shire_related_items`, `field_type: "related_content"`, `allowed_types` text and picture) and "Shire gallery" (vocabulary `shire_gallery`, `field_type: "media"`, `allowed_types` picture), both with `allowed_workflows` in_progress and published and `multiple_items` enabled up to 5. `main` carries no vocabulary with a `field_type` at all, so neither field can render under it, and the only comparable field in any committed snapshot is "Image gallery 33" on `legacy`'s editor3 profile, which `legacy`'s dataset makes unusable for these cases. The content is three text items ("Bree bulletin", "Rohan dispatch", "Weathertop note") and three pictures ("Gondor picture", "Mirkwood picture", "Fangorn picture"), all on the Sports desk working stage. The text items exist because `_validate_associated_items` words its refusal as `doc.get("headline", doc["_id"])` and `main`'s other Sports items have no `headline` (only a `slugline`), so a refusal naming one of them would read as a raw item id or as an empty string. Hand-crafted rather than recorded, like `compare-fields` and `authoring-header`: `storage:record` needs a MongoDB replica set for change streams. The three pictures share one set of GridFS renditions, copied byte-identically from `media-items`' "Rivendell picture" (`fixtures/metadata.jpg`), so the record carries one copy of the image and inherits the canonical `MEDIA_PREFIX` that `settings.py` rewrites - see the `media-items` entry below before adding any new media here. Cannot be ported into `main`: like `media-items` it adds items to the Sports groups, whose counts several specs assert exactly, and both fields would show up in every authoring view opened on the Story profile.

* media-items - `main` plus one item of every media type on the Sports desk working stage: "Rivendell picture" (picture), "Moria graphic" (graphic), "Isengard video" (video), "Lothlorien audio" (audio), and "Shire package", a plain package with no `highlight`, which `main` lacks because its only composite belongs to a highlight. Several specs assert exact item counts against `main`, so these items cannot be ported into it. Re-record it against a stack brought up with `SUPERDESK_URL=http://localhost:5000/api` (`e2e-up.sh` derives `SERVER_NAME` from that URL, and `e2e/server/settings.py` derives `MEDIA_PREFIX` from `SERVER_NAME`, so the backend stores the canonical prefix `http://localhost:5000/api/upload-raw`). On macOS, free port 5000 first: AirPlay Receiver answers there by default, which is why the everyday stack uses 5002. Rendition hrefs are absolute and are stored in the record, and `settings.py` only rewrites that one canonical prefix to whatever port the running instance answers on, so recording on any other port produces a snapshot whose thumbnails 404 everywhere but the instance it was recorded on. "Moria graphic" is a picture whose `type` was flipped to `graphic` directly in mongo and it keeps `profile: "picture"`, since no graphic content profile exists in the snapshot: it covers type filtering, not graphic authoring. The media was uploaded from `fixtures/` at the repo root: `metadata.jpg` (picture), `empty_metadata.jpg` (graphic), `metadata.mov` (video) and `audio.wav`, which exists only to give the audio item a source file.
